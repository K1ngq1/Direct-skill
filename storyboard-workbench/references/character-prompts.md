# 人物资产与可选细节 Prompt

人物资产和叙事分镜分开创作。基础人物图用于建立身份；痣、雀斑等主观细节另存为未启用的编辑 Prompt，不默认写入基础人物图、分镜正文或生成请求。不为每个人自动安排一颗痣或一层雀斑，也不因缺少这些细节扣分。已在原稿或实际参考中确定的细节属于原事实，不能当成可选项删掉。

## 基础人物 Prompt

按稳定资产 ID 读取本次已知的年龄、脸型、发型、体型、服装及来源，组织人物参考图 Prompt。先写人物，再交代一致的比例与服装、中性表情、简单背景、柔和光线及必要摄影约束，使身份和衣着读得清。独立视图按下节交付；用户可以明确调整画幅和视图形式，历史人物稿与三联图保留，不自动覆盖。沿用已有设定，不把独立镜头的愤怒、持物和场景动作固化成人物身份。摄影条件是本次导演设计，不冒充实拍参数。

已有确定采用的可用角色图时复用实际图片，不重新设计五官。本项目生成图须经用户确认后才能成为后续分镜参考，不能把完成出图等同于采用。只露手、衣袖或不需识别身份的辅助角色，不为凑资产表补头像或三视图。原稿明确不设面孔或基础身份缺口不可擅补时，保留待定状态与具体原因；人物细节提案不等于获准替这些角色确定长相。局部未具备条件不影响其他人物与分镜交付。

## 独立视图与已确认造型补图

默认在保留已有三联总览的基础上，为每个需要完整身份资产的人物补齐四张独立图片。每个视图一条 Prompt、一次只生成一张，不把四张当作同一提示词的四个备选，也不以裁出原拼图的一栏冒充新生成单张。没有既有图的新任务先按本次事实和导演设定建立身份，不伪造已确认参考；是否另做总览图按用户要求处理。

| 视图 | 默认画幅 | 必须保持的内容 |
|---|---|---|
| 正面全身 | 9:16 | 从头顶到脚底完整入画，面对镜头，双臂自然垂下，双手空着，服装与已确认造型一致。 |
| 侧面90度全身 | 9:16 | 沿用已确认参考的侧面，记录鼻尖朝画面哪侧；需要指定人物自身左侧或右侧时另写清相机侧别，不能把画面朝左等同于人物左脸。完整头脚，不回头。 |
| 背面全身 | 9:16 | 人物背对镜头，头部不回看，保留后脑、后背、衣服后部及鞋履结构。 |
| 正面大头照 | 1:1 | 单一正面近照，完整头顶、发际与下颌，保留少量肩部；耳部按既有发型自然遮挡，不为露耳改造型。中性表情、目视镜头，五官和年龄感可读，不变成年轻化或美容版本。 |

上述画幅与形式是可覆盖默认，不写成永久约束。已有明确的采用确认直接作为本次参考依据，记录人物ID、实际图片及用户要求，不重复确认同一造型。用户要求沿用现有造型时，补图保持原图的身份、发型、体型、服装与年龄感；这项确认不外推为用户已验收尚未生成的四张单图，也不外推到其他项目。

补图使用真实参考输入并核对每张结果；同一人物的左右定义、五官、发际线、服装结构和颜色跨视图一致。正面头像的取景变化不授权改脸，侧面不能露出错误侧别，背面不能擅自回头；不自动添加痣、雀斑、首饰或剧情道具。目标画幅与实际输出宽高分别核对，生成工具及并发规则按[工作流](visual-workflow.md#0-可调整的完整-prompt-与分阶段出图默认流程)执行。

## 主观细节单独保存

每项写清部位、人物自身左右、数量、大小感、颜色和疏密等真正需要控制的特征，写成独立局部编辑 Prompt。只能称“提案／未启用”，不能写成该人已经有的特征。不把痣、雀斑、疤痕等全部叠加成统一的所谓真实感模板。

编辑模板使用 `{{characterReference}}` 表示尚待绑定的实际人物图片。该位置是明确的未就绪模板语法，不是假图片名或可直接提交的 `@角色图`。只有人物图可用且用户明确要求这一项时，当前 Agent 才用实际引用替换，并按目标模型传入对应图像；未要求的提案继续停用。用户已说清人物与细节时直接理解执行，不重复确认同一要求；只请求编辑文字时不自动生图，实际图片编辑依本次用户要求和工具能力执行。

编辑只改所要求的局部，保留身份、五官比例、年龄感、发型、表情、服装、构图、光线及其他已有标记。人物自身左脸不随机位翻成右脸；痣的数量、位置不能在侧脸或跨镜中漂移。已有同一标记时按用户需要保留或调整，不重复再加。雀斑要避免整齐排列、浓重贴片或无依据蔓延。若当前图看不清目标部位，记录限制，不声称已经精确修改。

用户要求某一细节，只启用这一项；多项一起启用须有对应用户要求。生成结果不自动替换分镜身份图或代表用户采用。后续采用时再按稳定资产 ID 保存参考新版本与来源，生成图片不能伪称用户原始附件；核对依赖并保留旧图。确认后分镜优先引用新图，不向每镜再次展开整套人物细节。

模板库的 `state` 保持 `dormant`；用户提出具体需求后，另写本次已绑定实际图片的执行稿，不把模板库改为自动提交状态。用户这次的具体要求就是启用相应细节的依据，无须再让用户确认同一个要求。

## 独立数据与 Excel

基础图和可选编辑稿存于项目内 `character-prompts.json`，与冻结的 `visual-plan.json` 分开，避免可选提案进入分镜事实。以下为既有v1单 `base` 格式；新版资产依赖哈希按[工作流的v2合同](visual-workflow.md#资产总表与交接)。四张独立补图不塞进这一条基础正文，也不把旧导出或 `generation-manifest.json` 称为已支持多视图；继续v1项目时使用工作流规定的 `character-views-v1/` 附属计划和逐任务结果，保留旧三联图与冻结分镜。

既有v1格式：

```text
schemaVersion: 1
projectId: 对应冻结项目ID
sourcePlanHash: v1 使用 SHA256(JSON.stringify(对应visual-plan对象))；v2 使用 report 返回的 assetHashes.characters
characters: [{
  assetId: 对应productionInventory.characters中的稳定ID,
  base: {
    mode: generate | reuse | not-required | blocked,
    text: 基础人物Prompt（仅generate有正文）,
    referenceIds: reuse时该人物已实际绑定的图片ID，否则[],
    basis: 原设定、导演拍法或暂不生成的原因
  },
  optionalDetails: [{
    id: 人物内唯一细节ID,
    description: 尚未采用的具体提案,
    template: 含且仅含一个{{characterReference}}的局部编辑Prompt,
    state: dormant,
    requiresUserRequest: true
  }]
}]
```

正文由 Agent 创作，程序核对版本、资产、实际人物图片与停用状态，不自动编造外貌或选择细节。新文件不改变原分镜哈希及评分，也不自动将人物设定复制进分镜。缺少此文件的既有 v1 项目导出行为不变。v2 按资产依赖计算哈希；有人物时须覆盖全部人物，缺文件或 `blocked` 标为待处理；无人镜项目不要求空人物文件。`not-required` 须注明原因，具体版本规则见[新模式合同](visual-workflow.md)。

常规 `visual.mjs export` 在发现该文件时额外交付 `人物资产Prompt.xlsx`，包括基础人物 Prompt、可选细节编辑稿及使用条件；可选稿不会进入“最终Prompt”或人工评分正文。只新增人物交付时使用：

```text
node "<skill>/scripts/visual.mjs" export-characters "<project>"
```

该命令只导出人物工作簿，不改原评分或分镜文件；同名人物工作簿已存在时拒绝覆盖。修订时使用新版本或保留原文件，不能靠改项目哈希绕过人物语义核对。此导出命令不调用模型；实际图片生成、结果登记与资产确认按[分阶段流程](visual-workflow.md#0-可调整的完整-prompt-与分阶段出图默认流程)由当前 Agent 执行，不能把导出成功称为图片已经完成。
